## 2026-07-03  Docs get an HTML view layer, markdown stays canonical
Context: markdown docs read poorly and rarely get read. HTML reads better. But the pipeline docs are also the machine contract the agents read and write every run, so making HTML the source would raise tokens and diff noise and push HTML parsing onto every agent.
Decision: keep markdown as the single source of truth. Add scripts/render-docs.mjs, a zero-dependency, no-JS renderer that turns the human-facing docs (PRODUCT, PRD, DESIGN, ARCHITECTURE, DECISIONS, CONVENTIONS, STANDUP) into styled HTML under docs/html/ on one shared KaizenRise v3 stylesheet. Wired into /design, /architect, /standup. Machine-contract files (ROADMAP.yaml, story files, gate files, STATE, PROTOCOL, STRUCTURE, profile) stay markdown-only.
Consequence: agents keep writing cheap, diffable markdown. Humans read docs/html/index.html. The render is one-directional and docs/html/ is never hand-edited. New human-facing docs must be added to the MANIFEST in render-docs.mjs to appear.

## 2026-07-26  Prototype mode reads PRODUCT.md, and UX-PRINCIPLES ships to installs
Context: KaizenBridge reported that prototype mode's declared inputs were docs/PRD.md, docs/style-guide.html, and the target folder, with no docs/PRODUCT.md. The PRD says what the product does, the non-goals say what it must not do, and only PRODUCT.md carries the second. So the designer could render a forbidden affordance while following its own instructions correctly. Design mode reads PRODUCT.md, which is the asymmetry, the step that shows the founder a picture was blind to the constraints and the step that writes the contract was not. It produced real artifacts. prototypes/v2/console-revamp.html in KaizenBridge shipped two per-column Add story buttons and a Create story action, against a v1 non-goal of no writes beyond command dispatch. They survived many rounds of founder reaction, were approved, and were caught two steps later by design mode. Nothing shipped wrong, but a founder approved a picture he then had to reverse. Verifying that finding surfaced a second gap, docs/UX-PRINCIPLES.md is a declared input to design mode and was copied by neither install.sh nor update.sh, so the designer running inside any product was told to read a file that was not there.
Decision: prototype mode gains docs/PRODUCT.md as a declared input, a pre-draw check of the screen graph against the non-goals and hard constraints where stated, and a closing reconciliation of what was actually drawn, reported in the final message so the founder sees it before he reacts rather than after. Both run again on every re-render, because a founder reaction can introduce a forbidden affordance as easily as a PRD story can. A PRD story that implies something the non-goals forbid is a contradiction between two contracts, so it is named and stopped like a drift D3, not silently omitted and not resolved by the designer. The mechanism lives in .claude/agents/designer.md, /prototype names PRODUCT.md as the constraint source and relays a conflict before the reaction loop, and the reconciliation logic is not duplicated across the two. docs/UX-PRINCIPLES.md joins PROTOCOL.md and STRUCTURE.md as a contract, seeded by install.sh and overwritten by update.sh.
Consequence: the fix reaches every product on the next scripts/update.sh, which is why it was written into the harness and not into any product repo, since update.sh rm -rf's an installed .claude/commands and .claude/agents. The rule was deliberately not raised into docs/UX-PRINCIPLES.md alone, a principle in a doc is not read at draw time. Scope stays narrow, prototype mode only. Brand mode draws no affordances, and design mode already reads PRODUCT.md and demonstrably works. Products that installed before this update now receive UX-PRINCIPLES.md on their next update, so design mode's declared inputs become true for the first time.

## 2026-08-06  The doc renderer derives its set from disk, and reaps
Context: KaizenBridge reported (docs/UPSTREAM-2026-08-06.md in that repo) that scripts/render-docs.mjs held a third, independent list of what a founder doc is, alongside its own client nav and backend reader, with none derived from any other. The harness list was the one KaizenOS owns. It had drifted twice. Five docs present on disk were never in it, IDEAS, LEARNING, UX-PRINCIPLES and here also TRAINING and SHAKEDOWN, and they vanished from the render with no message, which is indistinguishable from an exclusion made on purpose. Separately, KaizenBridge's docs/html/IDEAS.html had outlived its manifest entry by eleven days, linked from nothing, because the renderer only ever wrote and never removed. The note's framing was that the list was "missing five", but two of those five, PROTOCOL and STRUCTURE, are excluded by the 2026-07-03 decision above and are not drift.
Decision: invert the default. Every docs/*.md renders except a named DENY set, currently STATE.md, PROTOCOL.md and STRUCTURE.md, which keeps the 2026-07-03 exclusion intact and makes it reviewable instead of implicit in an omission. The old MANIFEST becomes KNOWN, which supplies ordering, title and blurb only and gates nothing, so an unlisted doc still renders titled from its filename and sorted after the listed ones. The renderer reaps, deleting any .html in docs/html/ it did not produce this run, with index.html named explicitly since it is written after the loop and belongs to no doc. tests/render-docs.test.mjs covers both directions plus the two ways the reap could go wrong. Not taken: KaizenBridge's option 3, one shared definition module both the harness and a client import. It is the strongest fix and it is a new cross-repo contract surface, which is a bigger decision than closing a drift, and this change removes the harness's own reason to need it.
Consequence: a new founder doc appears in docs/html/index.html with no harness edit, and a removed one takes its page with it. Whether PROTOCOL and STRUCTURE should now get an HTML view, so a reader of the rendered docs has a route to the contracts at all, stays open and is Uma's call, one line in DENY either way. The prose describing the rendered set lived in three places and two of them were already stale, so docs/STRUCTURE.md was corrected with this and the header comment in the script rewritten. The 2026-07-03 consequence line, "New human-facing docs must be added to the MANIFEST in render-docs.mjs to appear", is superseded by this entry.

## 2026-08-06  PROTOCOL and STRUCTURE get an HTML view after all
Context: the entry above kept both in the renderer's DENY set, inherited from 2026-07-03, whose reasoning was that the agents parse and emit them every run so an HTML copy would only add tokens and diff noise. That reasoning covers the cost of the copy and never addressed the reader. KaizenBridge's note of the same day put it plainly, a person opening the rendered docs had no route to the contracts at all, and PROTOCOL.md and STRUCTURE.md are the two documents a human most needs to read here. Being parsed by an agent is not a reason to leave a person the raw markdown.
Decision: DENY drops to STATE.md alone. PROTOCOL and STRUCTURE render, with entries in KNOWN so they carry a real title and blurb rather than a derived one. STATE.md stays out on different grounds than the ones just retired, the loop rewrites it at the end of every story so its page would be stale more often than current, and it is four lines of pointer with nothing to lay out.
Consequence: the render stays one-directional and markdown stays the source, so nothing about the contract itself moves, only what a reader can open. Costs two more committed HTML files and their diffs on every contract change, which is the trade the 2026-07-03 entry declined and this one accepts. Installs that rendered STATE.html under an older list lose it to the reap, which is the one case update.sh's notice names.

## 2026-08-07  The board renders as static HTML from the harness, and KaizenBridge is held
Context: KaizenBridge was built to be the layer over a KaizenOS repo that shows the stories, the tasks, the acceptance criteria and the tests. It works, and it cost roughly 29,700 lines across a backend and a React frontend, with nine stories measuring $89.73 in subagent spend in one night. Its Console and Tests surfaces are 1,925 lines and exist only to dispatch, while Board, Docs and Standup together are 1,790 lines and are the whole of what a reader wanted. Uma's summary on 2026-08-07 was that a live app was never the requirement. Meanwhile scripts/render-docs.mjs already rendered every docs/*.md and never opened docs/ROADMAP.yaml, backlog/ or docs/gates/, which is where the state of a build actually lives. The spec was written first, at docs/BOARD-RENDER-SPEC.md, and committed here by the KaizenBridge session, which is not the route for a cross-repo finding and was Uma's call to accept.
Decision: the queue renders into the same docs/html/ the documents already render into. scripts/render-board.mjs reads ROADMAP.yaml, the story files and the gate records and returns pages; render-docs.mjs owns the output directory and the single reap over both page kinds. Three page kinds, the board on index.html above the document index, one page per epic, one page per story in the order the founder's own board used, lead then title then origin. It is a reading surface for a project manager, so the gate reads as sentences rather than a field dump and branch names and file paths do not appear. No server, no framework, no dispatch, no writes outside docs/html/. Both themes ship, light by default per v4 5.1, and the only JavaScript is the theme toggle. Wired into /next at step 12, after the state is written. KaizenBridge is held, not retired, and nothing in that repo was changed from here.
Consequence: every KaizenOS project gets the view for free on the next update.sh, which is why that script now carries a board-renders-static notice naming how many pages the next render adds to a committed directory. The YAML subset reader in render-board.mjs is new surface and is the piece most able to fail silently, so it is tested against the shapes that actually occur, a quoted finding carrying colons and commas and a flow-sequence depends_on. Two v4 status colors do not survive both grounds, warning #B8860B measures 2.79:1 on light and critical #C0392B measures 3.43:1 on dark, so the stylesheet splits status by theme and records every measured ratio in a comment. Those two are findings against the design system rather than against this render, reported to Uma, and v4 is not edited from this repo. Deferred to a second pass on Uma's call: logs/events.jsonl, so no per-story timeline and no cost block, since docs/COST.md already projects that trail.

## 2026-08-21  The code standards become a harness contract, docs/BUILD-STANDARDS.md
Context: the KaizenTasks build of 16 to 20 August 2026 left 19 gate files carrying 162 findings that a repair round then fixed. Read one by one, roughly a third were not one-off defects but eight shapes returning story after story, each buying a build round on every return. Broken citations, tests that cannot fail, drawn magnitudes never measured, writes with no failure path, a new query missing the predicate its sibling carries, a write that invalidates nothing, whole-batch rejection of model output, and a counted string assembled inline. Two of them recurred across three separate epics. The decisive evidence is not the recurrence, it is that one of the eight was already a written rule. That repo's CONVENTIONS.md recorded "read the section before citing it" on 19 August, upgraded from an observation to a rule because it had already happened twice, and it recurred four more times the next day. A rule with no stated way to see it broken does not hold.
Decision: docs/BUILD-STANDARDS.md joins PROTOCOL.md, STRUCTURE.md, UX-PRINCIPLES.md, TRAPS.md and SUCCESSION.md as a contract, seeded by install.sh and refreshed by update.sh. It holds only what is true regardless of stack and has recurred beyond one story, and every rule states the evidence that proves it rather than the principle alone. The planner and builder read it, qa judges standard 2 at the acceptance check, and the pr-reviewer walks all eight by name at the conformance step. The /next learn step now promotes a finding shape into that product's CONVENTIONS.md the second time a gate layer raises it, and names a cross-epic, stack-independent shape as a candidate for this file without promoting it, which stays a human call. A rule about one product's stack still belongs in that product's CONVENTIONS.md, which is project state and is never overwritten.
Consequence: the eight standards reach every product on its next scripts/update.sh, which is why they were written into the harness and not into the repo that produced the evidence. KaizenTasks is not touched by this change and applies it on its own next update. Contract text and reading lists only, no script rewrites and no new gate layer, so nothing in the loop gets slower. The file is deliberately small, and the bar for adding a ninth rule is recurrence across more than one product or epic, not a good idea.

## 2026-09-07  Architecture locked: single Next.js app, no separate backend service
Context: /architect for the Movie Info App (demo/internal tier, 7 stories: public browse/search, founder login-gated CRUD, visitor accounts and watchlist). The environment's global conventions default to a NestJS/Express backend plus a separate frontend, but this product has one editor, low traffic, and no requirement that outlives a single request/response cycle.
Decision: one Next.js 14 (App Router, TypeScript) app occupies code/frontend alone. Next.js Route Handlers under app/api/** are the API layer, satisfying "REST API" without standing up a second service. No code/backend slot.
Consequence: every future story that wants a genuinely separate service (a queue, a worker, a third-party integration with its own lifecycle) is a D3 contract change that must be argued for explicitly, not assumed from the environment defaults. Until then, all product code, public and founder-tool alike, ships from one deployable.

## 2026-09-07  One Auth.js instance, one users table, role column splits founder from visitor
Context: S-004 (founder login) and S-006 (visitor signup/login) both authenticate a user against a password, and both are in scope for v1. Building two separate auth systems (e.g. a hardcoded founder check plus a full user-accounts system) would duplicate password handling and session logic for no benefit.
Decision: one Auth.js (NextAuth v5) instance, Credentials provider, JWT session strategy. A single User table carries a `role` column (VISITOR default, FOUNDER seeded once via prisma/seed.ts, never self-service). Founder-only routes and API handlers check `session.role === 'FOUNDER'` server-side; the founder is not a config secret or env-var check, they are a real row with a hashed password like any visitor.
Consequence: password reset, if ever added, works identically for both audiences. The one security-sensitive thing this buys us that a separate system would not: a single place (the Credentials provider callback) to get password hashing, generic error messages, and session shape right, instead of two.

## 2026-09-07  Postgres + Prisma, schema lives inside code/frontend, no code/db slot
Context: docs/STRUCTURE.md's code/db slot exists for schema, migrations, and seeds "only when server-side persistence exists," which is true here (years, movies, users, watchlist all need durable storage). But nothing outside the one Next.js app touches the database directly.
Decision: Prisma schema, migrations, and seed script live at code/frontend/prisma/, not in a separate code/db slot. code/frontend is the only slot in code/.
Consequence: if a second service is ever justified (decision above), the Prisma schema becomes a real candidate to hoist into code/db at that point, since it would then be shared. Until then, splitting it out early would be organizing for a service that does not exist.

## 2026-09-07  No formal OpenAPI/Swagger spec for v1
Context: the environment's global conventions call for REST with OpenAPI/Swagger. This product's API surface is entirely internal, consumed only by its own Next.js client components, with no external integrator and no public API product.
Decision: Route Handlers stay REST-shaped (resource paths, JSON, proper status codes) and are documented in prose in docs/ARCHITECTURE.md section 3, rather than generating and maintaining a machine-readable OpenAPI spec with no external consumer.
Consequence: if a third party ever needs to integrate against this API, generating an OpenAPI spec at that point is a small, well-scoped follow-up story, not a rework, since the handlers are already REST-shaped.

## 2026-09-07  Posters and streaming links are founder-entered URLs, no upload pipeline
Context: S-005-AC1 lists poster as a field the founder fills in when adding a movie. Building real file upload (storage bucket, image processing, CDN) is a meaningful chunk of infrastructure that PRODUCT.md's v1 scope does not ask for.
Decision: poster and streaming-link fields are plain URL strings the founder pastes in (a poster URL from wherever they source it, or a path under code/frontend/public/ for a locally-hosted image). No S3/object storage, no upload widget, no image processing pipeline in v1.
Consequence: DESIGN.md's founder-edit form field is a URL input, not a file picker, which is worth restating since the design doc's layout note (3.8) mentions "poster upload" in the component list; that will need a design note reconciling it to a URL field when S-005 is planned, flagged here so /plan does not silently pick one interpretation.
