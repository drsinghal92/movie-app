## Story
As the founder, I want to log in to a protected area, so that only I can edit the site's content.

## Origin
PRD story block, `**Added.**` marker. /ideate.

## Acceptance criteria
- [x] **AC1.** When the founder enters correct credentials, the system grants access to the editing area.
- [x] **AC2.** When anyone enters incorrect credentials, the system denies access and shows an error.
- [x] **AC3.** A visitor who is not logged in cannot reach any editing page.

## Out of scope
Multiple founder accounts, password reset flow.

## Context
PRD: E02 / S-004. DESIGN: Founder login. ARCHITECTURE: Auth.js Credentials provider, JWT sessions, `role` column, `code/frontend`.

## Tasks

Goal-backward from the three criteria. At the end: a founder with correct
credentials reaches a role-gated page (AC1); wrong credentials stay out and see
a generic inline error that never leaks whether the email exists (AC2, per
ARCHITECTURE 7); an unauthenticated visitor hitting any `/founder/*` editing
route is redirected to the login before the page renders (AC3, enforced at the
route level not by hiding a link, per DESIGN 3.7).

The schema `User.role` (FOUNDER | VISITOR), the `prisma/seed.ts` founder user,
and the `next-auth` + `bcryptjs` deps already exist from the architect scaffold,
so this story wires auth, not the model. The protected page here is a minimal
FOUNDER-only placeholder; S-005 fills in the real editing tool over the same
gate. Two identifiers are pinned for every downstream task: the Auth.js instance
in `src/lib/auth.ts` exports `{ auth, handlers, signIn, signOut }`, and the
gated route group is `src/app/founder/*`.

- [x] **T1** `[backend]` Configure Auth.js: Credentials provider with bcrypt compare, JWT session carrying `role`, generic error on any bad credential -> `code/frontend/src/lib/auth.ts` -> satisfies AC1, AC2
- [x] **T2** `[backend]` Mount the NextAuth route handlers -> `code/frontend/src/app/api/auth/[...nextauth]/route.ts` -> satisfies AC1, AC2
- [x] **T3** `[backend]` Add middleware redirecting unauthenticated `/founder/*` (excluding `/founder/login`) to the login route -> `code/frontend/src/middleware.ts` -> satisfies AC3
- [x] **T4** `[frontend]` Build the founder login page: centered card, email + password + submit, busy state, inline generic error on failure, redirect to `/founder/edit` on success -> `code/frontend/src/app/founder/login/page.tsx` -> satisfies AC1, AC2
- [x] **T5** `[frontend]` Add the minimal FOUNDER-only placeholder editing page that server-side checks `session.role === 'FOUNDER'` -> `code/frontend/src/app/founder/edit/page.tsx` -> satisfies AC1, AC3
- [x] **T6** `[test]` Playwright e2e driving the real login form submit: correct creds reach the edit page (S-004-AC1), wrong creds stay out with a visible error (S-004-AC2), logged-out visit to `/founder/edit` redirects to login (S-004-AC3) -> `code/frontend/tests/e2e/founder-login.spec.ts` -> proves AC1, AC2, AC3

## Test plan
How this story is proven. The command scripts/test.sh runs.

`scripts/test.sh` runs `code/frontend`'s `typecheck` then `test` (`vitest run &&
playwright test`). The durable proof is the Playwright spec in T6, which drives
the actual login form (real field entry and submit, not a substitute POST) per
the PROTOCOL UI verification clause, and exercises the middleware redirect for a
logged-out visitor. The spec relies on the seeded founder user
(`prisma/seed.ts`) being present in the test database that `playwright.config.ts`
runs the build against.
